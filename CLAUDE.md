# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev           # Start with nodemon (auto-reload) — primary dev workflow
npm start             # Start production server (node index.js)
npm run lint          # ESLint check (eslint.config.js, flat config)
npm run lint:fix      # ESLint with autofix
npm run format        # Prettier write (.prettierrc.json)
npm run format:check  # Prettier check only, no writes
npm run swagger:generate  # Regenerate src/docs/openApiSpec.json from the live routers
```

`npm test` runs the `node --test` suites under `src/**/__tests__/`. Full API reference for every endpoint lives in `docs/API_DOCUMENTATION.md`. Every doc is indexed in `docs/README.md` (with links to all five Nura repos); the system-wide architecture lives only in the app repo's `docs/ARCHITECTURE.md`. When a change touches endpoints, env keys, infrastructure or security, update `docs/API_DOCUMENTATION.md`, `docs/INFRASTRUCTURE.md` or `docs/SECURITY.md` (including its "Production status" table) in the same PR.

**Swagger UI** (`/api-docs`, raw spec at `/api-docs.json`, `src/docs/swagger.js`) serves the committed `src/docs/openApiSpec.json`. That file is generated by `src/scripts/generateSwaggerSpec.js`, which imports the routers mounted in `index.js` and walks their stacks. Auth in the spec comes from each route's real middleware (`authenticate`/`optionalAuth`). Summaries come from the `@route`/`@desc`/`@access` JSDoc above each route, and 402s come from `FEATURE_ROUTES`. Re-run `npm run swagger:generate` after adding or changing a route, and write the JSDoc block so it gets a summary. A new route file also needs a `determineTag` mapping; the script warns if one is missing. Swagger is off in production unless `SWAGGER_ENABLED=true`.

A Husky `pre-commit` hook runs `lint-staged` (ESLint --fix + Prettier --write) on staged `*.js` files — commits fail if either can't auto-resolve the issue. Markdown/JSON/`package-lock.json`/`logs/` are excluded from Prettier via `.prettierignore`.

Environment variables are loaded from `.env` (see `.env.example` for the required keys: `MONGODB_URI`, `PORT`, `JWT_SECRET`, `JWT_EXPIRE`, `BCRYPT_ROUNDS`, plus third-party service keys for Firebase, Cloudinary/S3, Cashfree, Resend, Sarvam).

## Architecture

Node.js/Express REST API (ESM, `"type": "module"`) with MongoDB/Mongoose, plus a raw WebSocket server sharing the same HTTP server instance.

**Request flow**: `index.js` wires up middleware (helmet, cors, rate limiting, JSON body parsing, morgan→winston HTTP logging) then mounts one router per domain under `/api/<domain>` (auth, cycle, habits, consultation, partner, health-issues, blogs, content, community, nominations, wellbeing, reels, forest, buddies, newsletter, contact, upload, documents, reports, speech, voice-agent, subscriptions). Each domain follows `routes/ → controllers/ → models/`, with `schemas/` (express-validator) used only where request validation is defined (currently auth, marketing).

**Subscriptions / feature-wise paywall** (`subscriptionController.js`/`subscriptionAdminController.js`, `models/{SubscriptionFeature,SubscriptionPlan,SubscriptionSettings,Entitlement,Coupon}.js`, `utils/{subscriptionAccess,couponAccess}.js`, `middleware/subscriptionMiddleware.js`, `config/subscriptionRouteRegistry.js`): a per-feature catalog (`SubscriptionFeature`, keyed by a stable `key` like `ai_assistant`) that admins toggle free/premium and price individually from the Content Studio, plus optional `SubscriptionPlan` bundles of feature keys. `SubscriptionSettings` is a singleton with the global `subscriptionEnabled` switch — when off, `subscriptionAccess.js#getUnlockedFeatureKeys()` returns the `'ALL'` sentinel and every gate passes, so shipping this system changed no behavior until an admin opts in (every seeded feature also starts `isPremium: false`, see `utils/subscriptionSeedData.js`).

Enforcement is **fully registry-driven, not scattered per-route**: `config/subscriptionRouteRegistry.js` exports `FEATURE_ROUTES`, a flat array of `{ key, method, path }` (path as a RegExp against `req.path`), and `subscriptionMiddleware.js#globalFeatureGate` is mounted once in `index.js` *ahead of every domain router*. For every request it does one cheap array scan; on a match it runs `authenticate` (req.userId isn't set yet at this point in the chain) then `requireFeatureAccess(key)` before the request ever reaches its real route handler — which is why none of the individual route files (`questionAnswerRoutes.js`, `documentRoutes.js`, `screeningRoutes.js`, `voiceAgentRoutes.js`, `schemeApplicationRoutes.js`, `communityRoutes.js`, `partnerRoutes.js`, `cycleRoutes.js`, `buddyRoutes.js`) have an inline `requireFeatureAccess(...)` call anymore — the registry is the single source of truth for "what's gated." **To add a new gated feature: (1)** add one `{ key, method, path }` entry to `FEATURE_ROUTES` pointing at the *actual* endpoint a screen calls (grep the app's `lib/api.ts` for the real caller first — don't assume from a route file's name alone; `nominationRoutes.js`'s `/api/nominations` looks like "buddy nomination" but has zero client callers today, while the real Period Buddy nominate action is `buddyRoutes.js`'s `/api/buddies/:matchId/nominate`), **(2)** add a matching row to `utils/subscriptionSeedData.js` (`isPremium: false`) so it's visible/priceable in the admin Features tab, restart the server once to pick both up. Nothing else needs touching — an admin flipping that key's toggle enforces it immediately, no further deploys. A `SubscriptionFeature` with no `FEATURE_ROUTES` entry is priced/toggleable in the admin UI but enforces nothing anywhere (harmless but inert — check for this before assuming a toggle "isn't working").

It 402s with a `FEATURE_LOCKED` body carrying the feature's price and any plan that includes it, so the mobile app's paywall never needs a second round trip. Purchases (`POST /api/subscriptions/order` → `POST /api/subscriptions/verify`) are one-time period purchases via the same Cashfree Orders + order-status-verify pattern as `consultationController.js` (no Cashfree Subscriptions/webhooks/auto-renew — `Entitlement.expiresAt` is just `startedAt + 30d/365d/never`, and the user re-purchases to renew). `GET /api/reports/health-report` is deliberately **not** in the registry even though it backs the priceable "health_reports" feature — it also powers the free Graphs & Reports dashboard; the app enforces that one client-side instead (see period-buddy's `documents.tsx`). Admin CRUD for the catalog lives under `/api/admin/subscriptions/*` (settings/features/plans/coupons/overview), gated on `subscriptions.*` permissions (App Admin changes go through approval — see Admin Workspace RBAC), audited via `recordAudit`.

**Coupons** (`models/Coupon.js`, `utils/couponAccess.js`, `subscriptionController.js`'s `previewCoupon`/`createSubscriptionOrder`): admin-defined discount codes (`percentage` 1–100 or `flat` currency amount, always matched uppercase), store-wide rather than scoped to a specific plan/feature. `POST /api/subscriptions/coupons/apply` previews a code's discount against a specific plan/feature without redeeming it; `POST /api/subscriptions/order`'s optional `couponCode` re-validates independently and actually redeems on success (never trust the preview alone). `Coupon.redeemedCount` only increments on a *confirmed* redemption — either `/verify`'s atomic pending→active claim, or immediately for a 100%-off code — never on an abandoned pending order. A coupon that brings the price to ₹0 skips Cashfree entirely: the `Entitlement` activates immediately server-side and the order response carries `free: true`, which the app (`PaywallModal`'s `finishFreeUnlock`) uses to skip the checkout sheet altogether.

**Voice agent / outbound check-in calls** (`voiceAgentController.js`, `utils/samvaadClient.js`): `POST /api/voice-agent/converse` is the in-app text/voice chat loop (Sarvam chat completion, `api.sarvam.ai`). `POST /api/voice-agent/checkin-call` (private) triggers a real phone call — "Buddy" cycle check-in — via Sarvam's own **Instant Outbound** product (`apps.sarvam.ai`, informally called "Samvaad" in this codebase but not a separate vendor; distinct host + `X-API-Key` auth from the `SARVAM_*` chat/TTS/STT keys). Requires `SARVAM_OUTBOUND_API_KEY`/`SARVAM_ORG_ID`/`SARVAM_WORKSPACE_ID`/`SARVAM_APP_ID`/`SARVAM_APP_VERSION`/`SARVAM_CONNECTION_ID`/`SARVAM_AGENT_PHONE_NUMBER` (see `.env.example`) — `isSamvaadConfigured()` gates the endpoint (503 otherwise). `POST /api/voice-agent/checkin-call/webhook` is **public** (Sarvam can't send our JWT) — it's Sarvam's required call-completion callback, correlated back to a user via a signed, short-TTL JWT (`webhook_config.metadata.callToken`, verified server-side; `userId` is taken only from its decoded claim, never trusted verbatim from the payload), and is the **backup** save path. The main one is the agent's own in-call `log_cycle_entry` tool, which POSTs to `/api/cycle/log` with the per-call `user_auth_token`. The call's date is fixed once, in IST, when the call is placed (`utils/checkinCall.js#checkinDateKey`). The agent gets it as `call_date` (the tool's `dateKey` is bound to it, never LLM-chosen), and the webhook gets it as the `dateKey` claim in `callToken`, so a hallucinated/misheard date from STT can't overwrite an unrelated day's log. The Sarvam agent's post-call variables are named after `CycleLog` fields (`flow`, `mood`, `symptoms`, `sleepHours`, …), and the webhook saves only the fields today's log is still missing (`buildCheckinBackfill`), through the same shared `upsertCycleLog` (`cycleController.js`) the REST endpoint and `/converse` use. A value the tool or the user already saved always wins. The backend also sends `period_timing` ("expected in 3 days") and `call_weekday`, so the agent never does date arithmetic. The agent (`SARVAM_APP_ID`) is pinned by `SARVAM_APP_VERSION` to a **committed** version: edits in the Sarvam dashboard land in the draft and reach production only after a commit and a bump of that env var. `API_BASE_URL` must be the `www` host — the bare `backend.thenura.care` domain 301-redirects, which breaks Sarvam's POST callback.

**Check-in call scheduling** (`utils/checkinCallScheduler.js`, `utils/checkinCall.js`, `models/CheckinCall.js`): every call attempt, manual or automatic, is a `CheckinCall` document (source, the user's local `dateKey`, the `cycleKey` it counts against, Sarvam status, derived `outcome`, duration, summary, `retryAt`). `CycleSettings.checkinCallMode` is `'period_daily'` (one answered call on each of the `periodLength` period days) or `'once'` (period start + `checkinCallDayOffset`; the default, for schedules saved before the field existed). The tick runs every minute. It resolves the user's local date from `checkinCallTimezoneOffsetMinutes` (IST if missing) and computes predictions *for that date* (`resolveCallDay`, which checks both the current and the next period start, since `computeCyclePredictions` always puts the next start strictly after today). It then asks `planScheduledAttempt`. The day's first call may go out up to 2 h after the chosen time, so a restart doesn't lose it. A day with any answered call (manual included) is done. Retries happen only after `no_answer`/`failed` (+30 min / +10 min) or a callback request (the agent's post-call `callback_time`, else +60 min), at most 3 automatic attempts a day, and default retries never after 21:30. The unique `(userId, dateKey, attemptNumber)` index is the claim that stops two ticks dialing twice. The webhook sets `outcome`/`retryAt` (`classifyCallOutcome`/`planRetry`), turns the schedule off on `opted_out`, and sends at most one push (saved → `/tracker`, missed → `/tracker`, calls off → `/checkin-call`). "Call me now" is limited by `checkManualCallLimit` (3 a day, 10 min apart, 409 while a call is in flight, 429 otherwise), and a Sarvam refusal is a friendly 503, not a 500. Calls are capped at 5 min by the agent (`max_interaction_time_seconds`). The agent gets `call_reason`, `cycle_context`, `recent_log` and `last_call_summary` so each day's call continues the last one.

**Admin push broadcasts** (`adminNotificationController.js`, `models/PushBroadcast.js`, `utils/pushBroadcastWorker.js`, routes under `/api/admin/notifications/*` in `adminRoutes.js`): the admin creates a broadcast and gets a `202` back. An in-process worker then walks the audience's users in `_id` order, cursor-paged in batches of ≤500 (`PUSH_BROADCAST_BATCH_SIZE`, `PUSH_BROADCAST_BATCH_DELAY_MS`). Each batch goes out in one FCM `sendEach` via `fcm.js#sendPushBatch`, dead tokens are `$unset`, and `cursor` + counters are saved on the `PushBroadcast` doc after every batch. Delivery is at-least-once: a crash between a batch's send and its cursor save re-sends that one batch. A lease (`leaseUntil`) keeps two instances off the same job, and `startBroadcastWorker()` (called from `index.js`) resumes queued jobs and expired-lease running jobs on boot, then again every 5 min. Two lanes: `bulk` (role/everyone, one at a time, and the create endpoint 409s while one is in flight) and `direct` (`audience: 'selected'` with explicit `userIds`, capped at 5000), so a DM to a few users never waits behind a full-base blast. In-app inbox rows are written with `Notification.insertMany`, which deliberately skips that model's `post('save')` per-user push hook. Otherwise every user would get the push twice. An optional `route` (in-app path like `/tracker`, validated by `utils/notificationRoute.js` — no full URLs) on create/test is stored as `PushBroadcast.data.route` and sent as FCM `data.route`; the app's tap handler opens it. Users with `notificationsEnabled: false` (the app's Profile → Notifications toggle) still get the inbox row but no device push — same rule in `Notification`'s post-save hook — and aren't counted in `totalWithToken`/`hasDevice`. Users who hide notification details (`privacySettings.hideNotificationDetails`, default on) get the neutral text from `utils/privacy.js#pushFor` on every device push, admin test pushes and broadcasts included: the worker splits each batch with `splitTokensByPrivacy` into a real-text send and a neutral-text send, and the test endpoint answers `detailsHidden: true`. The inbox row keeps the real text. Every FCM message (`fcm.js#buildMessage`) carries `android.priority: 'high'` and `android.notification.channelId: ANDROID_CHANNEL_ID` ('default'), which must match the channel the app creates in `lib/notifications.ts`. Dead tokens are pruned from both `sendPushBatch` and single `sendPushNotification`; `messaging/invalid-argument` only counts as dead when the error blames the registration token (it's also returned for a malformed payload, which must not wipe everyone's token). `POST /api/logout` (and `/api/auth/logout`) unsets the caller's `notificationToken` — only if it equals the optional body `fcmToken` (the logging-out device's own token, so logout on phone A doesn't silence phone B), or unconditionally when `fcmToken` is absent (older app builds); best-effort, never fails the logout (`utils/logoutToken.js`) — and `POST /api/auth/fcm-token` strips the same token from any other account first.

**Scheduled / repeating pushes** (`models/PushSchedule.js`, `utils/pushSchedule.js` (pure recurrence math, IST wall-clock), `utils/pushScheduleRunner.js`, CRUD in `adminNotificationController.js`, routes `/api/admin/notifications/schedules*`): a schedule stores the message + a rule (`startAt`, `repeat` none/daily/weekly/monthly, `interval`, `daysOfWeek`, `endAt`, `maxRuns`). The runner ticks every minute (started from `index.js`, always on, unlike `ENABLE_IN_PROCESS_SCHEDULER`). It claims a due occurrence with a compare-and-set on `nextRunAt`, so it is safe with more than one instance, then creates a normal `PushBroadcast` (`scheduleId` set) and enqueues it. Delivery, history, cancel and retry of each send are the broadcast pipeline above. An occurrence more than 1h overdue is skipped (`skippedCount`), not sent late. Approval uses the same rule as a broadcast (wider than 25 picked users → `push.broadcast`); a repeating schedule approved after its first slot starts at the next one.

**People & letters / HR documents** (`constants/hr.js`, `utils/hrValues.js` + `utils/hrPdf.js` (pure, unit-tested; pdf-lib + bundled DejaVu fonts in `src/assets/fonts`), `models/Hr{Member,Template,Document,File,Counter}.js`, `controllers/hr{,Sign}Controller.js`, `routes/{hrRoutes,signRoutes}.js`):
- Super Admins (`hr.manage`) keep team member records and upload Canva-exported PDF templates. A template is either `fixed` (fields drawn at positions) or `letterhead` (a body laid out on the letterhead).
- Staff generate PDFs and email them, with a public e-signing link (`/api/sign/:token`, SHA-256-hashed token).
- PDFs live in MongoDB (`HrFile`) on purpose: the S3 bucket is public-read and letters include salaries.
- The design and contract are in the Admin Workspace repo's `docs/hr-documents.md`.

**Security & privacy** (`docs/SECURITY.md` is the source of truth, with the deploy checklist and breach runbook): revocable sessions (`utils/sessions.js`; every login is a `UserSession`, tokens carry its `sid`, `resolveToken` is the one place tokens are checked, for REST, optional auth and WebSockets), field-level encryption of health free text (`utils/fieldEncryption.js` + the `encryptFields` plugin on the models; production refuses to start without `DATA_ENCRYPTION_KEYS`; encrypted fields can't be queried, so never add a filter, sort or aggregate on one), private medical documents (`PUBLIC_PREFIXES` in `utils/s3.js`, signed view links), AI consent (`utils/privacy.js`, `requireAiConsent`), data export (`utils/dataExport.js`, keep it in step with `purgeAccount`), 30-day purge of deleted accounts (`utils/accountPurgeRunner.js`) and log redaction (`redact` in `utils/logger.js`). A new model holding personal data needs: `encryptFields` for its free text, a line in `purgeAccount`, and one in `buildDataExport`.

**Sign-in protection & retention** (`utils/loginSecurity.js`, `utils/sessionCookie.js`, `utils/retentionRunner.js`, `models/LoginChallenge.js`): per-account lockout after `LOGIN_MAX_FAILURES` wrong passwords; a "new sign-in" email for unseen devices (`privacySettings.newSignInAlerts`); staff and doctors get a second step: their authenticator app / recovery codes if they set one up (`utils/totp.js`, `controllers/twoFactorController.js`, `/api/auth/2fa/*`, `User.twoFactor` with the secret encrypted; resets at `/api/admin/staff/:id/reset-2fa` and `/api/doctor/admin/:id/reset-2fa`), otherwise an emailed code when `STAFF_2FA_ENABLED=true` (`POST /api/auth/login/verify-code`, `/resend-code`; Google sign-in refused for them); check-in call tokens carry a `scope` and only reach `POST /api/cycle/log` / the webhook (`scopeAllows`); staff logins that send `X-Session-Mode: cookie` get an httpOnly `nura_staff_session` cookie when `STAFF_COOKIE_AUTH=true`, read by `tokenFromRequest` in `authMiddleware.js` (Bearer wins; cookie writes need an allowed Origin). `User.privacySettings` (`PUT /api/auth/privacy/settings`) holds `hideNotificationDetails` (neutral push text via `utils/privacy.js#pushFor`, default on), `aiChatRetentionDays` and `newSignInAlerts`. `retentionRunner` deletes old notifications, audit logs, usage counts and per-person AI chats every 6 h. `encryptFields` has a `json` option for whole objects (screening `answers`). A new per-user field that's a preference belongs in `privacySettings` + `describePrivacySettings`.

**App CMS** (`constants/appCatalog.js`, `utils/appConfig.js` (pure validation/merge, unit-tested), `utils/launch.js` (launch states, unit-tested), `utils/appConfigStore.js` (section saves + revisions), `utils/launchScheduleRunner.js`, `models/{AppConfig,AppBanner,AppConfigRevision,LaunchInterest,LaunchStat}.js`, `controllers/appConfigController.js`, `routes/{appConfigRoutes,cmsRoutes}.js`): remote control of the mobile app from the separate **The-Nura-CMS** portal.

- **Storage:** `AppConfig` is a singleton (`key: 'app'`) that stores only *overrides*, split into five sections: `features` (built-in tiles plus admin `customTiles`, sharing one `order` per placement), `homeSections`, `screenSections` (block order/visibility for Profile and the three hubs, keyed by screen, plus hub `screenTitles`; every block on every screen can also carry a `text` override, an `audience` and `startAt`/`endAt`; `SCREEN_SECTIONS` marks `required` blocks that can move and be renamed but not hidden, targeted or scheduled), `theme` and `settings` (maintenance mode, update prompts). `merge*` helpers lay them over the catalog defaults, so an empty DB is the app as shipped.
- **Placements:** the three hubs plus `home`/`profile` (Shortcuts blocks), so "move a feature to another screen" is just a placement change.
- **Tap actions:** `route` / `url` / `app`. `app` is another app's link with an https fallback, with code-running schemes blocked.
- **Audiences:** segment, platforms and app-version range, evaluated client-side (fine, since they're not security gates).
- **Launch states** (`utils/launch.js`; design in The-Nura-CMS `docs/launch-states.md`): each feature/link tile has `launch.state` of `live` / `coming_soon` / `rolling_out` / `paused`, plus testers, a sticky-hash rollout %, Notify me and go-live/resume schedules. Unlike audiences these are resolved **server-side per caller** in `GET /api/app-config` (optional auth + `X-Device-Id`), which is why that response is `private` with `Vary`. Builds that don't send `X-Nura-Launch: 1` get non-open items as `enabled: false`.
- **Feature usage** (`utils/featureUsage.js`, `models/FeatureUsage{,Device}.js`): the app's batched `POST /api/app-config/usage` beacon counts opens (screen visits) and tile taps per item per UTC day; `GET /api/cms/usage` feeds the CMS's Usage page.
- **Banners:** a separate collection (`AppBanner`), with a `popup` placement, scheduling, and click and impression beacons.
- **Reading:** the app reads `GET /api/app-config` with `Cache-Control: no-cache` (ETag revalidation). Don't make it `max-age`: iOS and browsers then serve a stale copy after a publish, which is exactly the "theme didn't update" bug this replaced.
- **Adding a feature, placement or section needs both repos:** a value an app build doesn't know is ignored by that build.
- **Permissions:** writes need `cms.manage` (App Super Admin, Super Admin); reads need `cms.read` (App Admin and up).
- **Versions:** there's a global `version` (the app's cache key) and a per-section `sectionVersions.<section>` (the CMS's optimistic lock), so a banner or theme save never makes an open Features editor stale. `saveSection` never upserts with the version filter. `ensureConfig()` (which awaits `AppConfig.init()` for the unique index) creates the doc, then the versioned update runs without upsert. A missing counter (a doc saved before counters existed) counts as 0.
- **History:** every publish writes an `AppConfigRevision` (last 50 per section). Restore re-validates the snapshot against today's catalog before republishing.
- **Theme:** tokens are limited to brand, surface and text (`THEME_TOKENS`). Danger colours, overlays and shadows stay app-side.

**Gen Z pack** (`utils/genz.js` (pure, unit-tested), `constants/cycleSync.js`, `controllers/{genzController,circleController}.js`, `routes/{genzRoutes,circleRoutes}.js`, `models/{CycleSyncTip,BestieCircle,CircleVibe}.js`, `utils/circleMembership.js`): four app features, all read-only over existing data except circles. `GET /api/genz/wrapped` (month/year recap + a mood "persona"), `GET /api/genz/era` (today's phase as an "era" plus phase-matched cycle-syncing tips), `GET /api/genz/badges` (current/longest streak + `BADGE_CATALOG`, computed per request, so no stored badge state and nothing to backfill), and `/api/circles/*` (Bestie Circles: ≤8 members, ≤5 circles per user, 6-char invite codes without 0/O/1/I/L, 7-day TTL vibes, reactions, rate-limited hype). Circle pushes are `type: 'system'` with `data.kind` (`circle_join`/`circle_support`/`circle_hype`) and `data.route: /circles?id=<id>`; only an `askForSupport` vibe pushes the whole circle, so plain status updates stay quiet. Tips are CMS-edited (`/api/cms/cycle-sync-tips*`): while `CycleSyncTip` is empty the app gets the defaults; the first CMS create copies the defaults in first, and from then on the database is the only source (deleting every tip brings the defaults back). The four features are `FEATURE_CATALOG` keys `wrapped`/`cycleEra`/`badges`/`circles`, placed on Home's Shortcuts by default. Account deletion leaves every circle via `leaveAllCircles` in `accountLifecycle.js`.

**Auth**: JWT-based. `authMiddleware.js` exposes `authenticate` (required), `optionalAuth`, and `authorize(...roles)` for role gating. Decoded token attaches `req.user` (full Mongoose doc) and `req.userId`. Token verification/signing lives in `utils/jwt.js`. **Suspended accounts** (`isActive: false` set by an admin — distinct from a self-deleted account, whose email is rewritten to `deleted_…`; see `utils/accountStatus.js#isSuspended`): `login` checks suspension only *after* the password matches (so it can't be used to probe emails), and `googleAuth` after the ID token verifies; both answer `403` with `code: 'ACCOUNT_SUSPENDED'` and fire `notifySuspendedLoginAttempt()`, which emails the owner (reply-to `SUPPORT_EMAIL`, default `hello@thenura.care`, the address the marketing site and API docs publish) at most once per 24h via an atomic claim on `User.suspensionNoticeSentAt`. `authenticate` answers `401` with the same `code` for a user suspended mid-session — 401, not 403, because every client (Admin Workspace's `handleUnauthorized()`, the app's `onUnauthorized`) already signs out on 401; the code only lets a client say why.

**Signup rules shared with the app**: `lastName` is optional everywhere (`User`/`PendingSignup` default it to `''`; build display names with a join that skips it, never `${firstName} ${lastName}`). `utils/password.js#validatePasswordStrength` (8+ chars, lower, upper, digit, any non-alphanumeric symbol) is mirrored by The-Nura-App's `lib/password.ts` signup checklist: change both together, or the app will accept passwords this rejects.

**Account lifecycle** (`utils/accountLifecycle.js`, `utils/accountStatus.js`): one module decides what happens to linked data when an account goes away. Add a new per-user model there, not in each controller. `softDeleteAccount` (in-app `DELETE /api/auth/delete-account`) keeps the User row with `deletedAt` set and the email renamed to `deleted_<id>_<email>`. It hides the user's posts, strips their comments/likes/poll votes from other people's posts and reels, severs partner links on both sides and ends buddy matches (each notifying the counterpart), removes nominations, cancels open consultations, unsets the push token and turns off reminders and check-in calls. `purgeAccount` (public `/api/auth/account/delete/confirm`, which also matches soft-deleted rows by their original email via `findAccountsByOriginalEmail`) does all of that and then hard-deletes the data plus S3 objects under `medical-documents/<id>/` and `users/<id>/` (the generic upload endpoint now writes there). Paid consultations are kept with their contents stripped, so doctor earnings don't change, and Entitlement/CouponRedemption rows are kept as payment records. `suspendAccount` (admin suspension, staff suspension/removal) is reversible: it only closes sockets, ends buddy matches and cancels pending ChangeRequests. Partner readers, schedulers, the Notification push hook, WebSocket upgrade/room joins and doctor listing refuse inactive accounts themselves. `isSelfDeletionBlocked` stops staff and doctors from self-deleting. A deleted account can't be reactivated (`setUserStatus` 409s). The invite set-password link no longer flips `isActive` back to true. ChangeRequest replay refuses (and cancels) a request whose requester is gone, inactive, no longer staff or re-roled. `retireDoctorProfiles` (doctor deactivation) hides the profile, slots and reels and cancels open consultations; paid ones are logged as `consultation_refund_required`, since there is no automated refund. `seeder.js` backfills accounts deleted before this existed.

**Admin Workspace RBAC** (`config/permissions.js`, `middleware/rbac.js`, `middleware/approvalGate.js`, `controllers/{staff,changeRequest}Controller.js`, `models/ChangeRequest.js`): staff roles are `admin` (Super Admin — kept as the literal `'admin'`, holds every permission), `content_super_admin`/`content_admin`, `app_super_admin`/`app_admin`, and `clinical_admin`. Admin routes gate on **permissions** via `requirePermission(...)`, never on role strings — reshaping a role is a `permissions.js`-only change. `authorize('doctor')` is still used for the clinician portal. Lower-tier staff hold `x.write`/`x.send` but not `x.publish`/`x.manage`/`x.broadcast`; routes wrapped in `withApproval({ key, directPermission, department, needsApproval?, snapshot?, summarize? }, handler)` let direct holders straight through and turn everyone else's request into a pending `ChangeRequest` (HTTP 202 `{ pendingApproval: true }`). Approving (`POST /api/admin/change-requests/:id/approve`) **replays the stored params/query/body through the same controller** (`replayChangeRequest`, acting as the requester), so approval runs identical validation and side effects — the handler is looked up by `key`, which must be unique. Content Admins can still create and edit *drafts* directly (`draftOnlyUnlessPublisher` forces new items to draft; `needsApproval` only fires for live items). Staff are invited from `/api/admin/staff/*` (hierarchy in `canManageRole`: Super Admin manages everyone; a department super admin manages only lower levels of their own department; the last active Super Admin can't be demoted/suspended) and accept via the same `/api/doctor/set-password` link as doctors. Login and set-password responses carry `data.access` (role label, department, permissions) for staff.

**Deployment** (`docs/INFRASTRUCTURE.md` = full overview of what runs in production; `infra/README.md` = setup guide): production runs as Docker on a single EC2 host — `Dockerfile` (Node 20, non-root, tini) plus `deploy/docker-compose.yml` (the API + Caddy for HTTPS/WebSockets, logs to CloudWatch `/nura/api`). One CloudFormation stack (`infra/cloudformation/backend.yml`) creates the VPC, instance, ECR, Secrets Manager secret `nura/api/env`, and a CodePipeline: GitHub `main` → CodeBuild (`buildspec.yml`: lint, test, build + push image) → CodeDeploy (`appspec.yml` → `deploy/scripts/{install,start,validate}.sh`; a failed `/health/ready` auto-rolls back). The container's environment is **only** that secret (JSON object, rendered to `/opt/nura/app.env` at deploy time; update with `infra/scripts/push-env-to-secret.sh`, then re-run the pipeline) — a new env var needs to be added there, not just to `.env.example`. Keep it to **one** API container: WebSocket rooms and `utils/inProcessScheduler.js` are in-process state.

**Error handling**: Controllers throw/pass errors to `next()`; centralized in `middleware/errorHandler.js`, which normalizes Mongoose `ValidationError`/`CastError`/duplicate-key (11000) and JWT errors into consistent `{ success, statusCode, message }` JSON. `notFound` handles unmatched routes. Responses elsewhere should use `utils/sendResponse.js` (`sendError`/success helpers) for consistency.

**Pagination** (`utils/apiHelpers.js`): `getPagination(req.query, { limit, maxLimit })` → `{ page, limit, skip }` and `buildPagination({ page, limit, total })` → `{ page, limit, total, pages, hasNextPage, hasPrevPage }`. New list endpoints return `data: { <items>, pagination }`. When adding pagination to an endpoint that **already returns a bare array**, don't change `data`'s shape — installed app builds and older admin bundles read it directly. Instead make paging opt-in with `isPaginatedRequest(req.query)` (true only when `?page=` or `?limit=` is sent; otherwise keep the old response exactly) and respond with `sendPaginatedList(res, message, data, pagination, extra)`, which puts `pagination` (and e.g. `unreadCount`) next to `data` on the envelope. Endpoints done this way: `GET /api/partner/notifications` (also `unreadCount` over all notifications; without params still the newest 50), `GET /api/questions/sessions` (without params the newest 100), `GET /api/doctor/consultations` (+ `?search=` on patient name, among that doctor's patients), `GET /api/doctor/admin/list`, `GET /api/admin/subscriptions/coupons` (+ `?search=` on code). `GET /api/doctor/payments?page=` instead adds `pagination` inside its existing `data` object, with `total`/`count` still summed over all paid consultations. Still capped with no paging (older items unreachable): the chat-message endpoints (partner/buddy/consultation, 300 newest) and the embedded arrays in `GET /api/community/:id` comments and `GET /api/questions/sessions/:id` messages.

**WebSocket layer** (`src/config/websocket.js`): shares the HTTP server via `server.on('upgrade', ...)`. Auth is via a `token` query param verified with the same JWT util as REST; unauthenticated connections are allowed only where `token` is absent. Clients are auto-joined to a personal room `user_<userId>` and tracked in in-memory `rooms`/`clientMetadata` Maps (no external pub/sub — single-process only). Used for real-time features like buddy chat/consultation messaging, and for pushing async document-extraction results (see below). `partnerController.disconnectPartner` broadcasts `partner_disconnected` to both sides' `user_<userId>` rooms (and creates a `system` Notification — hence a push — for the other side): the mobile app keeps a partner's role on-device, so this event is how a viewer disconnected by the owner gets moved out of the partner view immediately.

**Document extraction** (`documentController.uploadDocument` + `utils/sarvamClient.js`): uploaded medical documents (PDF or image) are saved to S3 and the `Document` record is created with `extractionStatus: 'pending'` immediately — OCR/text extraction via Sarvam's doc-digitization job API runs *after* the response is sent (fire-and-forget `runExtraction`), since the remote job can take well over a minute. On completion the document is updated and a `document_extraction_update` event is broadcast to the uploader's `user_<userId>` WebSocket room; there is no polling endpoint, so clients must listen on that socket (or re-fetch the document) to learn when extraction finishes.

**Background/startup**: `utils/seeder.js` runs once after `connectDB()` resolves in `index.js` to seed initial data.

**Domain-specific integrations** live under `src/utils/`: `fcm.js` (Firebase push, service account from `FIREBASE_SERVICE_ACCOUNT_JSON` env — raw or base64 JSON — or else `firebase-service-account.json`), `s3.js` (AWS S3 uploads, also used alongside Cloudinary for media), `cashfreeClient.js` (payments), `sarvamClient.js` (speech-to-text/TTS, backs `speechRoutes`), `googleAuth.js` (Google OAuth login), `mailer.js`/`otp.js` (email + OTP flows), `careSuggestionsAi.js`/`caringEngine.js`/`reportContext.js` (AI-driven care/report logic for cycle & wellbeing features), `cycle.js` (period cycle calculation logic).

**Logging**: `winston` logger (`utils/logger.js`) is the standard — always log via `logger.info/error/warn` with an `action` field and structured context (see existing calls), not `console.log`. HTTP access logs go through `morgan` piped into winston (`utils/httpLogger.js`).

**Models** are grouped by feature area with feature-specific relations, e.g. buddy matching (`BuddyMatch`, `BuddyMessage`), consultations (`Consultation`, `ConsultationMessage`, `Doctor`, `DoctorAvailability`), community (`Community`, `Comment`, `CommunityLike`), cycle tracking (`CycleLog`, `CycleSettings`), habits/gamification (`Habit`, `HabitCompletion`, `RewardTransaction`, `ForestLog`), and document Q&A (`Document`, `DocumentChatMessage`).

Rate limiting (`express-rate-limit`, `middleware/rateLimiters.js`) is active, not commented out: `apiLimiter` (500 req/15min, mounted on `/api`) plus a stricter `authLimiter` (20 req/15min, IP-keyed) and an email-keyed `otpEmailLimiter` guarding the sensitive endpoints in `authRoutes.js` (login, signup, OTP request/verify, account-deletion codes) via `sensitiveLimiter`/`otpLimiter`. Auto-enabled in production and toggleable via `RATE_LIMIT_ENABLED` (off by default outside production, so local dev isn't throttled).

## Token-usage hygiene

A `.ignore` file excludes large/generated files (`package-lock.json`, `logs/`, the service-account blob under `src/utils/`) from broad search tools (Grep/Glob/Explore) so they aren't scanned or dumped into context during exploration. These files are still directly readable by exact path when actually needed — the exclusion only affects untargeted searches. Don't remove entries from `.ignore` without a reason; add new ones if a large/generated file shows up in the repo.
